# Microsoft Exchange Server Provider

~> **Use at your own risk.** This is a community project, maintained on a best-effort basis and provided as is, without warranty (MIT license). Each release is tested by hand on a lab before it is published; nothing is tested continuously against an Exchange Server organization. Run `terraform plan` and try your configuration on a non-production organization before applying it to production.

The Microsoft Exchange Server provider manages the configuration of an on-premises Exchange organization as code: mail flow rules, accepted and remote domains, Outlook on the web and mobile device policies, email address policies, retention policies and organization settings. Exchange Online is managed by a separate provider, [workplace-as-code/msexchangeonline](https://registry.terraform.io/providers/workplace-as-code/msexchangeonline/latest).

The provider is **experimental**: see [Resources and availability](https://registry.terraform.io/providers/workplace-as-code/msexchangeserver/latest/docs/guides/availability) for what has been tested.

When something fails, start with the [Troubleshooting guide](https://registry.terraform.io/providers/workplace-as-code/msexchangeserver/latest/docs/guides/troubleshooting).

It opens an Exchange remote PowerShell session through scripts embedded in the provider binary. The machine running Terraform needs:

- Windows, joined to the Active Directory domain of the Exchange organization, with Windows PowerShell 5.1 (built into Windows). No PowerShell module needs to be installed: the cmdlets come from the Exchange server.
- An account with the **Organization Management** role group, or equivalent. The connection uses Kerberos with the FQDN of an Exchange server, with the account's password or, with `auth_method = "integrated"`, as the account Terraform runs as (a CI runner service or a scheduled task). See the [Authentication guide](https://registry.terraform.io/providers/workplace-as-code/msexchangeserver/latest/docs/guides/authentication).

## Example Usage

```terraform
terraform {
  required_providers {
    msexchangeserver = {
      source  = "workplace-as-code/msexchangeserver"
      version = "~> 0.1"
    }
  }
}

# Terraform runs on a Windows machine joined to the domain: the provider opens
# an Exchange remote PowerShell session with Kerberos.
provider "msexchangeserver" {
  server   = "exch01.contoso.local"
  username = var.username
  password = var.password
}

resource "msexchangeserver_remote_domain" "partner" {
  name                 = "Partner"
  domain_name          = "partner.example"
  auto_forward_enabled = false
}
```

Edge Transport servers are managed with a separate provider block whose `role` is `Edge`: see [Edge Transport servers](https://registry.terraform.io/providers/workplace-as-code/msexchangeserver/latest/docs/guides/authentication#edge-transport-servers).

Every argument can also come from an `EXCHANGE_*` environment variable: `EXCHANGE_ROLE`, `EXCHANGE_SERVER`, `EXCHANGE_AUTH_METHOD`, `EXCHANGE_USERNAME` and `EXCHANGE_PASSWORD`. A value set in the provider block takes precedence over the environment.

## Attributes left out of the configuration

Every resource only manages the attributes set in its configuration. An attribute left out is never written: a new object gets the Exchange default, and an existing object keeps its current value, which is recorded in the state. Importing or adopting an object therefore never changes it until you set an attribute. The exception is the conditions and actions of `msexchangeserver_transport_rule`, which define the rule: a condition left out means the rule has none.

## Schema

### Optional

- `auth_method` (String) How the provider authenticates with the `Mailbox` role. `password` (default): `username` and `password`. `integrated`: Kerberos with the Windows identity of the process running Terraform, for example a CI runner service or a scheduled task on a domain-joined machine; `username` and `password` must then be left unset. `certificate`: HTTPS with the client certificate given by `certificate_thumbprint`, which Active Directory maps to the account. `integrated` and `certificate` are not available with the `Edge` role. Can also be set via the `EXCHANGE_AUTH_METHOD` environment variable.
- `certificate_thumbprint` (String) With `auth_method = "certificate"`, the thumbprint of the client certificate, in the Personal store of the Windows account running Terraform (`Cert:\CurrentUser\My`), with its private key. Spaces are ignored. With several servers or a load balancer name, each name must match the HTTPS certificate of the Exchange servers. Can also be set via the `EXCHANGE_CERTIFICATE_THUMBPRINT` environment variable.
- `domain_controller` (String) FQDN of the domain controller every session reads from and writes to (`Set-ADServerSettings -PreferredServer`), so that two runs served by different Exchange servers see the same data. If it is unavailable, the connection fails. Leave it out to let Exchange choose. `Mailbox` role only. Can also be set via the `EXCHANGE_DOMAIN_CONTROLLER` environment variable.
- `password` (String, Sensitive) Password of `username`. Not used with `auth_method = "integrated"`. Can also be set via the `EXCHANGE_PASSWORD` environment variable.
- `role` (String) Role of the server the provider connects to: `Mailbox` (default) manages the organization; `Edge` manages an Edge Transport server, whose resources are limited to its own settings. Use one provider block per Edge server, with an alias. Can also be set via the `EXCHANGE_ROLE` environment variable.
- `server` (String) FQDN of the Exchange server. With the `Mailbox` role, the FQDN registered in Active Directory (e.g. `exch01.contoso.local`): the connection uses Kerberos, which fails with an IP address or a short name; a DNS alias or load balancer name needs an alternate service account (ASA), see the Authentication Guide. Required, either here or via the `EXCHANGE_SERVER` environment variable, unless `servers` is set. With the `Edge` role, the name WinRM reaches the Edge server with; leave it out when Terraform runs on the Edge server itself.
- `servers` (List of String) FQDNs of Exchange servers, as registered in Active Directory, tried in order: each connection goes to the first server that accepts it, and servers whose `/PowerShell/healthcheck.htm` does not answer 200 (down or in maintenance) are tried last. Use it instead of `server`. An authentication failure is not retried on the next server. Exchange chooses the server that runs the commands, whatever server the provider connects to: the list does not cover the failure of that server. `Mailbox` role only. Can also be set via the `EXCHANGE_SERVERS` environment variable, comma-separated.
- `username` (String) With the `Mailbox` role and `auth_method = "password"` (default), the Active Directory account used for Exchange Server, as `CONTOSO\svc-terraform` or `svc-terraform@contoso.local`. With the `Edge` role and a `server`, a local administrator of the Edge server, as `EDGE01\Administrator`. Required in both cases, either here or via the `EXCHANGE_USERNAME` environment variable.

## Performance tuning

The provider keeps a few PowerShell processes open during a run and reuses their Exchange connection. These environment variables tune that behavior:

| Variable | Default | Effect |
|---|---|---|
| `EXCHANGE_MAX_CONCURRENCY` | `4` | Maximum number of PowerShell processes running at once |
| `EXCHANGE_SCRIPT_TIMEOUT` | `10m` | Maximum duration of one bridge call |
| `EXCHANGE_BRIDGE_MODE` | `persistent` | `oneshot` starts a new PowerShell process for every call |
| `EXCHANGE_WORKER_MAX_REQUESTS` | `200` | Requests served by a PowerShell process before it is replaced |
| `EXCHANGE_BRIDGE_DIR` | unset | Run the bridge scripts from this folder instead of the embedded copy (script development only) |
